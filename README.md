### Data Accuracy

The information in this repository has been collected through the reading and analysis of IDs from NCMC cards. Operator and station mappings are performed manually and may contain errors.

## Data Model

Two tables with a strict parent/child relationship:

```text
operators                         stations
─────────────────────────         ──────────────────────────────────────
acquirer_id  (1 byte, hex)  ◄──┐  id
operator_id  (2 bytes, hex) ◄──┼─ acquirer_id ┐ foreign key to operators
name                           └─ operator_id ┘
station_file (e.g. cmrl.csv)      terminal_pattern  (3 bytes, X = wildcard, or NULL)
                                  name
                                  comments
```

- **`operators`** is the master list. `(acquirer_id, operator_id)` is the primary key, so an operator can exist only once.
- **`stations`** holds every station or terminal-ID pattern, each belonging to exactly one operator. There is one shared table rather than one table per operator, so adding an operator never requires changing the schema. The per-operator lists are what you get by filtering on the operator, and what `export_csv.py` writes out as separate files.
- IDs are stored as uppercase hex text without `0x`, which keeps them readable in any SQLite browser. The database rejects malformed IDs, duplicate patterns within an operator, and stations that point at a non-existent operator.
- Station **names are not unique**: interchange stations legitimately appear under several IDs (for example Ameerpet in `hmrl.csv`).
- A `NULL` terminal pattern means the station is known but its ID has not been decoded. An empty `name` means the ID has been seen but not yet named.
- The read-only view `v_stations` joins both tables for easy browsing.

## Quick Start

Requires Python 3.9+ and nothing else (the `sqlite3` module ships with Python).

### Add IDs from a Metrodroid dump

```bash
python scripts/ncmc_lookup.py my_card.json
python scripts/export_csv.py
```

`ncmc_lookup.py`:

1. **Filters personal data.** Only an allowlist of fields is read: the effective date and, per transaction, the acquirer/operator/terminal IDs, minutes elapsed, sequence, amount, status and RFU. The card number, serial/UID, holder name, balance and any unrecognised field are ignored. Their names (never values) are listed so you can see what was dropped. The allowlist is at the top of the script.
2. **Shows the history with real times.** The card's effective date is the epoch and each transaction's `minutesElapsed` is added to it, giving a date and time to the minute.
3. **Looks everything up** in the database, honouring wildcard patterns.
4. **Prompts for anything new**: operator name and export file name, station name, terminal pattern (with a suggested mask) and optional comments. Pressing Enter on a name skips that item.
5. **Asks before saving.** Nothing is written until you confirm, and Ctrl-C leaves the database untouched.

Only operator IDs, terminal IDs and the names you type are stored. Timestamps, amounts and balances are shown on screen but never written to the database. Use `--no-prompt` for a read-only report.

### Add or change data by hand

```bash
python scripts/ncmc_db.py operators
python scripts/ncmc_db.py stations "Chennai Metro"
python scripts/ncmc_db.py add-operator 0x0B 0x177D "Chennai Metro" --file cmrl
python scripts/ncmc_db.py add-station 0B:177D 0x001XXX "Airport"
python scripts/ncmc_db.py add-station 0B:177D - "Mannadi" -c "?"        # ID not decoded yet
python scripts/ncmc_db.py edit-station 12 --name "Alandur" --comments "? Name shortened"
python scripts/ncmc_db.py find hyderabad 0x323149
python scripts/ncmc_db.py check
```

An operator can be given as `ACQ:OPERATOR` in hex or as part of its name. The database can also be edited directly in any SQLite tool such as DB Browser for SQLite; the constraints in `schema.sql` still apply.

### Export CSVs for Metrodroid

```bash
python scripts/export_csv.py             # writes export/
python scripts/export_csv.py --out DIR   # or elsewhere
```

The output format is the same as before the migration: `operators.csv` with `acquirer_id,operator_id,operator_name,terminal_info`, plus one `terminal_id,station_name,comments` file per operator.

### Run the tests

```bash
python -m unittest discover -s tests -v
```

### Duplicate Prevention and Updates

The database enforces most of the old CSV rules itself:

- An operator `(acquirer_id, operator_id)` can exist only once, and every station must belong to an existing operator.
- A terminal pattern can exist only once per operator. Before proposing a new station, `ncmc_lookup.py` checks exact IDs **and** wildcard masks, so an ID already covered by a mask such as `0x123XXX` is never added again.
- When a new pattern overlaps an existing one, the tools show the overlap and (in `ncmc_lookup.py`) ask for confirmation.
- Operators that still have stations cannot be deleted.
- Existing rows are never rewritten by the lookup script, except to give a name (and optionally a mask) to a row that was recorded without one.
- Rows keep their insertion order, so regenerated CSVs produce small, reviewable diffs.

## 9. CSV Update and Duplicate Prevention

Database update tools should preserve existing information.

### Append-Only Updates

When adding a new operator or station:

- Existing rows must not be deleted.
- Existing station IDs must not be overwritten.
- New entries should be appended only after duplicate checks.
- Existing station files should not be rewritten unnecessarily.
- A missing final newline must be handled before appending a new CSV row.

### Operator Duplicates

The combination of Acquirer ID and Operator ID uniquely identifies an operator.

Before adding an operator, check whether the same combination already exists in `operators.csv`.

Do not create duplicate operator entries.

### Station Duplicates

Before adding a terminal ID, check:

1. Exact terminal ID matches.
2. Wildcard matches using existing `X` masks.
3. Complete CSV row matches, where applicable.

Only append the row if it is genuinely new.

### Missing Station File References

If an existing operator has an empty `terminal_info` field:

1. Generate the operator-specific station filename.
2. Assign the generated filename to `terminal_info`.
3. Persist the updated value in `operators.csv`.
4. Create the station file if it does not exist.
5. Add the new terminal entry after performing duplicate checks.

Existing operator rows must be preserved when updating the file.
